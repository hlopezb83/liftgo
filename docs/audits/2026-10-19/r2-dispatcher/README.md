# R2: booking cancellation and hidden active invoices

Audited base: `7ac56b7b904f79fdb0b194dbccd97d67f364273a`.

**REVIEWABLE PROPOSAL — BLOCKED for merge/publication:** 0106 currently protects status-based invoice issuance, but does not yet protect the fiscal claim of a draft (`cfdi_status=stamping`) before PAC submission. A cancelled booking could therefore cause a status=sent persistence rejection after an external CFDI was issued. Parent review must resolve that explicit predicate/claim contract before activation. No migration has been applied to a published backend.

## Baseline stage (tests only)

The initial baseline commits of `booking-invoice-cancellation-api.spec.ts` add 21 expectations against the existing ephemeral A/B backend. Four fixture-state controls and two billing RPC lock-order cases bring the second baseline to 27. The current proposal has 32 cases, adding organization inference on RPC create, successful/contended pivot UPDATE, recurring cursor lock upgrade with two bookings, and concurrent two-booking invoice issuance. ASUS has no running local Supabase stack; proposal results remain pending the existing A/B CI lane.

The A/B seed adds disposable Auth dispatchers in both synthetic organizations and validates their roles. Every case logs in through `createLocalUserClient`, verifies Auth user, membership-derived organization and actual role, then uses ordinary PostgREST SDK requests for fixture rows, operations, reads and cleanup. Business rows use the default `is_e2e=false`. Dispatchers must still see no invoice rows. No role/credential/policy is changed in a published backend.

The matrix covers admin and dispatcher, RPC and direct UPDATE, direct and pivot invoice links, draft/cancelled controls, later draft emission, foreign organization denials, inverse links to cancelled bookings, and four overlapping issue/attach versus cancellation cases. Another two races start with a draft without pivots and a cancelled booking, then reverse the order of emission and new pivot attachment while both requests overlap. Whole invoice/booking/link snapshots verify rejected writes do not drift.

The lock coordinator uses the existing loopback `DB_URL` only for `SELECT ... FOR UPDATE` / `FOR SHARE` and lock observation. It performs no business mutation or JWT/GUC impersonation. Actual racing operations remain authenticated SDK requests. It forces both orderings without new RPCs, test triggers or timing sleeps: hold a booking to queue billing before cancellation, or hold an invoice to queue billing while cancellation commits. `pg_blocking_pids` confirms waiting before the next step. Two synthetic bookings are inserted high-UUID first, low-UUID second, with reversed RPC input. SHARE barriers on both bookings stop the recurring cursor before its first UPDATE, independent of the physical/query-plan row order, while invoice readers must finish. Timeout, `41P01`, coordinator errors or unexpected SQLSTATEs fail the tests. Locks are released and started requests settled even on failures.

## Migration 0106 prepared, not applied

`cancel_booking(uuid,text)` remains SECURITY INVOKER, including its existing row lock and guards. A private SECURITY DEFINER trigger will inspect same-organization active invoices on cancellation, including direct and pivot links, so that a dispatcher cannot bypass the rule through invoice RLS. The active predicate matches the current RPC: status outside draft/cancelled and cancellation not accepted. Pending cancellation remains active.

A cancellation-only trigger cannot protect the opposite order. Two private reciprocal guards cover invoices on activation/link/cancellation changes, and invoice_bookings on INSERT/UPDATE. Billing locks its invoice then reads booking status under FOR SHARE, rereading after lock acquisition. These readers are compatible with one another and FK KEY SHARE, but conflict with status UPDATE / NO KEY UPDATE. The cancellation side retains its NO KEY UPDATE writer mutex and reads invoices without locking them. The existing cancellation RPC keeps its original FOR UPDATE. This follows the [PostgreSQL 17 row-lock matrix](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

Only pivot UPDATE with changed identity uses invoice FOR UPDATE NOWAIT. It already owns the pivot tuple before its ROW trigger, so waiting could invert the save RPC's invoice -> DELETE pivot order. Contention returns exactly `55P03` with a neutral message containing “Reintenta”, rolls back the pivot update, and lets the RPC proceed. INSERT can wait normally. Unchanged pivot identity returns without new locks; a legitimate active-invoice UPDATE with a free invoice must succeed. This is an explicit retry tradeoff, not a hidden state reset or a claim of deadlock freedom for arbitrary bulk APIs.

All three new functions are VOLATILE SECURITY DEFINER with fixed search_path and explicit same-organization checks. The proposed REVOKEs apply only to these new private helpers (PUBLIC/anon/authenticated/service_role); there are no GRANTs, existing RPC ACL changes or dispatcher invoice SELECT grants. Trigger names sort after `trg_organization_write_context`, preserving RPC invoice/pivot INSERTs that omit organization_id. The catalog-only SQL supplement checks those contracts; real Auth/RLS cases remain in A/B.

Drafts can remain linked after booking cancellation; later activation is blocked. Unrelated edits of legacy inconsistent invoices must remain possible when lifecycle/link/cancellation fields do not change. The migration must not update existing business rows or grant invoice visibility to dispatcher.

The inspected `save_invoice_with_bookings` takes advisory billing locks, then the invoice row before syncing pivots. `sync_invoice_bookings` takes advisory locks but does not lock a booking row before the invoice. The current `create_recurring_invoice` takes advisory locks, inserts its new draft/pivots, then updates `bookings.last_billed_date`; its existing-invoice branch updates that booking cursor and returns without a later invoice mutation. New guards must not acquire advisory locks after the invoice row. Two tests overlap the actual save RPC and direct emission in both invoice-lock orders, preserving normal success or the existing `55000` stale-version rejection and rejecting a new deadlock. This is a bounded claim about these billing RPCs, not every unrelated booking mutation.

Fiscal pending/accepted states cannot be fabricated by an ordinary authenticated SDK because the existing fiscal metadata guard forbids it. A separate fixture-only extension preseeds four synthetic invoice snapshots through the existing seed admin, explicitly separate from the authenticated operation under test. Cases then attach them, read them, attempt cancellation and clean them up through ordinary SDK login. A negative SDK fiscal-metadata write verifies that the existing guard still rejects assigning accepted. No CFDI UUID, Facturapi id, PAC call or fiscal bypass is used.

The dispatcher migration slot is **0106**, after REP claim migration 0105. The journal and snapshot are chained, and the migration is DDL only: no existing business row is repaired or mutated. Local journal, TypeScript and lint checks do not certify SQL execution, published ledger state, the pending fiscal contract or permission to apply. See [migration execution contract](../../../migration-release-contract.md) for separate official preflight/application requirements.
