## Migration 0106 prepared, not applied

`cancel_booking(uuid,text)` remains SECURITY INVOKER, including its existing row lock and guards. A private SECURITY DEFINER trigger inspects same-organization occupied invoices on cancellation, including direct and pivot links, so that a dispatcher cannot bypass the rule through invoice RLS. The authorized fiscal predicate is identical in all three new guards: `cfdi_status = stamping`, or `(status outside draft/cancelled OR cfdi_status = stamped) AND cancellation_status != accepted`. Stamping remains occupied even with accepted cancellation; accepted stamped invoices release the booking. Pending/error drafts remain free. The invoice trigger includes UPDATE OF cfdi_status and its no-op comparison includes that field, so the actual claim attempts the reciprocal booking check before PAC.

A cancellation-only trigger cannot protect the opposite order. Two private reciprocal guards cover invoices on activation/link/cancellation changes, and invoice_bookings on INSERT/UPDATE. Billing locks its invoice then reads booking status under FOR SHARE, rereading after lock acquisition. These readers are compatible with one another and FK KEY SHARE, but conflict with status UPDATE / NO KEY UPDATE. The cancellation side retains its NO KEY UPDATE writer mutex and reads invoices without locking them. The existing cancellation RPC keeps its original FOR UPDATE. This follows the [PostgreSQL 17 row-lock matrix](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

Only pivot UPDATE with changed identity uses invoice FOR UPDATE NOWAIT. It already owns the pivot tuple before its ROW trigger, so waiting could invert the save RPC's invoice -> DELETE pivot order. Contention returns exactly `55P03` with a neutral message containing “Reintenta”, rolls back the pivot update, and lets the RPC proceed. INSERT can wait normally. Unchanged pivot identity returns without new locks; a legitimate active-invoice UPDATE with a free invoice must succeed. This is an explicit retry tradeoff, not a hidden state reset or a claim of deadlock freedom for arbitrary bulk APIs.

All three new functions are VOLATILE SECURITY DEFINER with fixed search_path and explicit same-organization checks. The proposed REVOKEs apply only to these new private helpers (PUBLIC/anon/authenticated/service_role); there are no GRANTs, existing RPC ACL changes or dispatcher invoice SELECT grants. Trigger names sort after `trg_organization_write_context`, preserving RPC invoice/pivot INSERTs that omit organization_id. The catalog-only SQL supplement checks those contracts; real Auth/RLS cases remain in A/B.

Pending/error drafts can remain linked after booking cancellation; later activation or fiscal claim is blocked. Unrelated edits of legacy inconsistent invoices remain possible when lifecycle/link/cancellation/fiscal fields do not change. The migration does not update existing business rows or grant invoice visibility to dispatcher.

The inspected `save_invoice_with_bookings` takes advisory billing locks, then the invoice row before syncing pivots. `sync_invoice_bookings` takes advisory locks but does not lock a booking row before the invoice. The current `create_recurring_invoice` takes advisory locks, inserts its new draft/pivots, then updates `bookings.last_billed_date`; its existing-invoice branch updates that booking cursor and returns without a later invoice mutation. New guards must not acquire advisory locks after the invoice row. Two tests overlap the actual save RPC and direct emission in both invoice-lock orders, preserving normal success or the existing `55000` stale-version rejection and rejecting a new deadlock. This is a bounded claim about these billing RPCs, not every unrelated booking mutation.

Fiscal states cannot be fabricated by an ordinary authenticated SDK because the existing fiscal metadata column ACL forbids it. A fixture-only extension preseeds four sent pending/accepted snapshots plus fourteen draft fiscal snapshots through the existing seed admin, explicitly separate from the authenticated operation under test. Cases then attach/read/cancel/clean up through ordinary SDK login. Draft stamping, stamping+accepted and stamped block cancellation; stamped+accepted, pending and error permit it, for both direct/pivot links. Two additional stamping snapshots test rejected ordinary SDK attachment to a second, already-cancelled booking through each guard. A negative SDK fiscal-metadata write still expects the existing 42501 column permission denial. No CFDI UUID, Facturapi id, PAC call or metadata bypass is used.

The real `handleStampCfdi`, authentication and organization checks were exercised offline with an injected claim transport result `data=null,error.code=23514`: response 409, zero PAC/config/fetch calls, exactly one claim attempt, no compensation writes/inserts/uploads/RPCs.
